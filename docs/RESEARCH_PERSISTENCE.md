# Research persistence configuration

The `app.db.research_repository.ResearchRepository` boundary writes run aggregates and normalized event/report rows to Supabase when configured. Production requires both `SUPABASE_URL` and one server-side credential: `SUPABASE_SECRET_KEY` (preferred) or the legacy `SUPABASE_SERVICE_ROLE_KEY`. Keep these values only in the API server's environment/secret manager; never put them in `NEXT_PUBLIC_*` variables or browser code. A missing Supabase configuration raises `ResearchPersistenceNotConfigured` whenever `ENVIRONMENT=production`. Outside production, the repository uses an atomic JSON-file replacement under `RESEARCH_LOCAL_STORAGE_DIR`, defaulting to `data/research` relative to the process working directory.

Apply `supabase/migrations/202610260001_research_persistence.sql` through the normal reviewed Supabase migration workflow before enabling the repository's Supabase path. It creates `research_runs`, `research_events`, and `research_reports` with run-linked cascade deletion. This repository change does not execute a migration against any live project. Confirm the resulting schema and server-role permissions in the target project before rollout.

`POST /research`, run lookup/list, event lookup, and report lookup now use the `ResearchRepository` boundary. In production the route fails closed with HTTP 503 if durable storage is not configured, and persistence failures are not silently redirected to local files. Supabase writes use the atomic `persist_research_record` RPC for the run aggregate, events, and report; local development writes use an atomic file replacement under `RESEARCH_LOCAL_STORAGE_DIR`. The API integration does not apply migrations to a live project. Before deployment, apply the ordered migrations and verify the RPC and service-role access in the target Supabase project.
